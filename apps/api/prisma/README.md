# Database schema and migrations

`schema.prisma` is the single source of truth for the database.

| Migration | What it does |
|---|---|
| `20261008000000_baseline` | Generated by Prisma from `schema.prisma`: all tables, enums, indexes and foreign keys. |
| `20261008000100_timescaledb` | Things Prisma cannot express: hypertables, compression, continuous aggregates, CHECK constraints, helper functions, triggers and reporting views. |
| `20261008000200_restrict_asset_history_deletes` | Asset history (maintenance, compliance, location, usage, scans, alerts, training, media) can no longer be cascade-deleted. Assets are soft-deleted via `deletedAt`. |

## Commands (run from `apps/api`)

```bash
pnpm db:migrate   # apply all migrations (prisma migrate deploy)
pnpm db:drift     # exit non-zero if migrations and schema.prisma disagree
pnpm prisma:migrate --name <change>   # create a new migration after editing schema.prisma
```

`db:drift` and `prisma migrate dev` need `SHADOW_DATABASE_URL` pointing at an
empty database with TimescaleDB available (docker-compose creates
`biotrakr_shadow`). CI runs both commands against a fresh TimescaleDB on every
change to `apps/api`.

## Rules for Timescale SQL in migrations

- Hypertables: pass `create_default_indexes => FALSE`, and make sure the model's
  `@@id` includes the time column. Otherwise the drift check fails.
- Declare indexes in `schema.prisma` (`@@index`) rather than in raw SQL, so the
  drift check sees them.
- Retention policies are deliberately off. Enable them only after a
  records-retention decision, because device history is compliance evidence.
